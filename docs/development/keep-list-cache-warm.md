# 持续保留全部列表首屏缓存

## Background
用户确认修正上一版短 TTL：全部分类、平台及 Skills 首屏应持续保存在 Redis，抓取提交后更新，并定期补热缺失/漏刷数据。复用已有列表范围、API/SSR 接入和发布流程决定，无 UI 变化。

## Scope
- 固定 50 组列表的数据和版本号长期保留，合法空列表同样保留
- 保留已有采集提交后的定向失效与回填、CAS 防旧写及 Redis 故障读库降级
- 服务启动及每 15 分钟补偿刷新，最多并发 2，失败范围重试一次，单轮 5 分钟截止；维护轮次不重叠
- 部署预热和定期补热保留旧数据至成功替换，失败不清空已有缓存

## Out of scope
新增来源、UI、分页/搜索缓存、Supabase schema/Cron 变更、既有页面/CDN 缓存策略和页面预热超时调整

## Acceptance criteria
- 正常/空列表和版本号 TTL 均为 -1，超过旧期限不因时间消失
- 旧版本的有限 TTL 键读取后迁移为长期保留
- 失效只影响对应范围，旧请求不能覆盖新结果，版本键淘汰时不能读孤儿数据
- 无访客访问时定时补热仍触发；失败后下轮恢复，旧数据不因补热失败丢失
- 生产 Node 运行时启动维护，开发/构建/Edge/未配置 Redis 不启动
- 翻译缓存 TTL、既有首屏游标和后续分页行为不变

## Feasibility
结论：可行。基于已 fetch 的 origin/master 152a34d，独立工作树 rss-site-list-cache 的干净 feat/keep-list-cache-warm 分支；主工作区包缓存删除不处理。沿用上次已确认设计，仅修正保留策略并增加已有单实例服务中的补偿任务，无新依赖或迁移。
- 生产复现：2026-11-03T03:50:12Z，50 个 generation 键，0 个 data 键；Redis expired_keys=49、evicted_keys=0。与数据 300–330 秒/空值 30 秒、版本 86400 秒的 Lua 及 TypeScript 实现一致
- Redis 列表键约 2 MiB，固定注册表范围有界；原 128 MiB allkeys-lru 预算继续生效，压力淘汰仍可能发生，补偿刷新和请求回填负责恢复
- 已读安装版 Next 16.3.4 instrumentation 指南和运行时实现：register 在服务启动调用，构建阶段跳过；动态导入限定 Node，异步刷新不阻塞服务准备
- 维护仅刷新 Redis。正常采集通知继续负责 Next 页面失效/CDN 发布；补偿不重发 IndexNow 或强制清除全部页面，既有页面 2/6 小时及 CDN 策略独立存在
- 复用已有 Supabase 公共只读查询及 10 秒截止，不修改查询接口、授权、RLS 或数据库结构

## Implementation
- Lua 的版本和数据键均去掉 EX，普通与空列表一律长期保留；读取旧版本遗留键时原子 PERSIST，版本缺失仍先删除孤儿数据
- 保留随机版本及 CAS；正常采集通知仍先定向失效再回填
- 部署内部命令改为直接强制刷新，不先清空全部列表；失败保留上一份有效数据
- Next Node instrumentation 动态加载后台维护，启动立即刷新，此后每 15 分钟运行一轮；不等待刷新完成才提供服务
- 每轮沿用并发 2、单查询 10 秒、整体调度 5 分钟截止，失败范围重试一次；进程内单计时器、单运行轮次，安全结构日志，不新增公开端点
- 维护只读 Supabase 并更新 Redis，不重复抓取、写库、刷新 Cron 或重发全部 CDN/IndexNow

## Risks
- Redis 故障时仍降级读库，内存压力仍可淘汰数据，长期保留不等于物理上永不丢失
- 补偿每轮约 51 次只读数据库请求；每 15 分钟约每日 4896 次，另有启动/失败重试与原采集刷新
- 通知丢失时 Redis 数据由下一轮补偿刷新；整页新鲜度还受既有页面/CDN 缓存约束
