# 线上 SEO 复核：2026-10-11

站点：https://news.ljhboard.cn/。检查时间：北京时间 2026-10-11 20:35 起。

结论：基本抓取与页面元数据已经上线；当前优先问题是没有实际答案的详情页仍可索引、历史内容缺少可抓取的分页入口，以及 sitemap 响应慢。聚合内容缺少独立信息价值也是需要验证的竞争因素。以上不能替代站长后台数据，不能据此断言排名下降、被处罚或某个问题导致了全部排名损失。

- 原始公共响应摘要存放于被 Git 忽略的 `.seo-cache/2026-10-11-seo-evidence.json`。不读取数据库或部署凭据，不改产品代码。

## 优先问题

### P1：无实质内容的详情页仍被提交索引

线上证据：

| 详情页 | 实际内容 | 索引状态 |
| --- | --- | --- |
| [知乎：如何做好吃的炒饭？](https://news.ljhboard.cn/social/zhihu/如何做好吃的炒饭--653dd714-7c0a-43f3-89c9-554695d43937) | 只有“求经验分享！”，没有答案 | 200、`index, follow`、在 sitemap 中 |
| [Hacker News 文章](https://news.ljhboard.cn/technology/hacker-news/scandinavia-s-first-farmers-slaughtered-hunter-gatherer--6c988ee7-8b0b-4dde-bbc1-17bfa5b99ecc) | 只有“Comments on Hacker News”和“Source”链接 | 200、`index, follow`、在 sitemap 中 |
| [新华社：世界市长对话](https://news.ljhboard.cn/news/xinhua/新华社消息丨-2026世界市长对话-洛阳-共话古都焕新与城市发展--7b430550-ebcc-48a5-af2b-99767bda6f17) | 内容只剩记者、编导、制作署名，没有报道正文或可观看视频 | 200、`index, follow`、在 sitemap 中 |

代码原因：`apps/web/components/article-reader.tsx` 的 `articleMetadata` 对所有存在的文章设置 `index: true`；`apps/web/lib/sitemap-service.ts` 直接读取文章元数据，没有内容完整性或索引资格过滤。

建议：先按内容类型识别链接占位、缺正文、缺媒体等确定性失败状态，统一控制详情页 robots 和 sitemap 资格。保留可读页面时使用 `noindex, follow` 并从 sitemap 移除，允许爬虫访问以读取 noindex。不要只按字数设置阈值；简短但完整的快讯仍可能有价值。

验收：上述占位案例不再进入 sitemap 且输出 noindex；完整文章、完整短讯和可播放的有效媒体不被误伤；后续补齐内容可恢复索引资格。[Google noindex 文档](https://developers.google.com/search/docs/crawling-indexing/block-indexing)

### P1：首批之后的历史文章缺少分页链接

代码证据：`home-article-list.tsx` 和 `event-timeline.tsx` 的后续批次由 IntersectionObserver 或“加载更多”按钮触发，访问 API 获得 nextCursor，没有指向独立列表页的下一页 `<a href>`。

首批服务器渲染正常，历史内容仍能通过 sitemap 被发现；缺陷是缺少连续的站内发现路径，不能断言历史文章完全无法收录。Google 爬虫通常不会点击按钮或触发需要用户交互的加载。[Google 分页指南](https://developers.google.com/search/docs/specialty/ecommerce/pagination-and-incremental-page-loading)

建议：保留滚动体验，同时增加可独立请求并服务端渲染的历史列表 URL 和下一页链接；每页使用自己的 canonical，不全部 canonical 到第一页。先覆盖重要栏目及来源，再评估时间轴。普通文章详情页也可增加少量有意义的同主题/同来源文章链接。

验收：关闭 JavaScript 时可通过链接读取第二批文章；任意抽样历史文章存在从栏目出发的分页发现路径；分页不存在重复首批或错误 canonical。

所有分片显示 `CF-Cache-Status: DYNAMIC`，虽然已发送 `s-maxage=7200`。分片 7 再次请求仍为 DYNAMIC，耗时 4,134 ms。说明本次请求未使用 Cloudflare 边缘缓存，不能据此断言源站完全没有缓存。

建议：确认当前 Next GET 路由实际缓存行为，缓存生成后的 XML，并让内容发布时失效；确认 Cloudflare 针对 sitemap 的缓存规则。先减少重复数据库工作，再考虑进一步缩小分片。避免在 sitemap 请求期间读取所有正文来计算内容质量。

验收：重复请求有可证实的缓存命中且不重复扫描数据库；文章新增、改动或移除后 sitemap 正确更新；记录冷/热耗时，而不是仅检查 Cache-Control。长耗时增加抓取成本，但当前请求成功，尚未证明搜索引擎获取失败。

### P2：中文目标与英文页面内容不匹配

AI 栏目首批含大量英文标题、摘要，抽查的 OpenAI 和 Simon Willison 页面原始正文为英文。译文通过用户点击按钮后 POST 获取，不是独立可抓取的中文页面。文章 schema 已识别为 `en`，但根布局的 HTML lang 固定为 `zh-CN`。

这是中文查询竞争力的潜在限制，不是已证实的索引阻断。应先用实际查询数据判断需求，再决定制作人工核验的中文解读或提供持久化、独立 URL 的中文版本。仅改变 lang 或批量自动翻译不能保证排名改善，也不应为同一个交互 URL 凭空加 hreflang。

### P2：聚合内容的独立价值不足

抽查的详情大多是来源正文、节选或摘要；AI 事件样本也只是来源的一段短摘要。对于文章原始标题，本站直接与原站竞争，不能仅靠 schema 或 metadata 推断能超越原站。

建议先做少量面向明确中文搜索意图的页面，例如经过人工核验的 AI 每周变化、模型更新比较、跨来源事件背景，提供来源之外的解释与证据，并建立稳定内链。关于页已有来源和更新频率说明，进一步补充真实维护者、纠错入口和编辑/翻译方法即可；不要虚构作者资历。[Google 有用内容指南](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)

### P3：小范围元信息问题

- 首页 title 实际为“今日热点 - AI、科技、新闻、财经与游戏热榜 · 今日热点”，品牌名称重复。可使用绝对首页标题，子页继续使用模板。
- AI description 列举了部分官方厂商，但现有栏目也包括个人博客，建议按真实范围更新文案。
- `articleMetadata` 最后用 `description` 覆盖生成器结果；summary 为空时没有 description。该项是代码风险，本轮样本没有确认具体缺失页面，宜使用真实内容回退，不应堆关键词。
- 英文页语言标记、可靠文章图片及分享图值得后续检查；没有证据将它们列为当前排名低的主因。

## 限制和实施顺序

- 没有站长后台权限、真实爬虫日志、关键词排名或外链数据，因此未计算综合 SEO 分数，也未宣称网站被处罚。

- 抽样来自六个分区的头尾及首页链接，不是随机总体样本，不能外推低质量页面比例。逐片读取时数据可能发生变化，没有验证所有分片属于同一个一致性快照。
- 下一步优先修复内容索引资格和 sitemap 缓存，再补抓取分页与站内关联。中文内容和原创选题应结合目标查询决定。

百度平台当前公开列出普通收录、索引量、流量与关键词、抓取诊断和抓取异常工具。优先确认本站已添加、sitemap 已提交且读取成功，并使用抓取诊断验证首页、中文新闻详情与历史列表。若后台提供普通收录 API 权限和配额，再评估在已有内容发布流程中增加百度通知；不要先全量推送 35,644 个候选 URL。[百度搜索资源平台](https://ziyuan.baidu.com/doc/)、[普通收录工具说明](https://ziyuan.baidu.com/college/articleinfo?id=267&page=2)

### Bing：IndexNow 验证文件可用，接收结果仍需后台或日志

`GET /indexnow.txt` 返回 200、32 字节，符合 key 格式；代码已使用显式 `keyLocation`。这验证了公开文件可读取，不代表最近批次的 IndexNow POST 成功，更不代表链接已经索引。现有代码还会在 Cloudflare purge 失败时跳过 IndexNow，需检查发布日志中通知是 succeeded、failed 还是 skipped。

优先在 Bing Webmaster Tools 的 IndexNow 面板和 URL Inspection 中查看最近提交、抓取及索引状态，确认 sitemap 有效，再检查 Search Performance 中的查询与点击。通知成功仅解决发现与更新提示，内容质量和索引选择仍由引擎决定。[Bing IndexNow 文档](https://www.bing.com/webmasters/help/indexnow-0z209wby)、[Bing 站长指南](https://www.bing.com/webmasters/help/webmaster-guidelines-30fba23a)

IndexNow 当前公开列出的参与端点包括 Bing，没有 Google 或百度。因此不能把现有 IndexNow 实现当作已经通知了这两家。[IndexNow FAQ](https://www.indexnow.org/faq)

### 公开搜索结果的具体限制

尝试打开 Google、Bing、百度的 `site:news.ljhboard.cn` 结果页，网页读取工具均报告无法访问。浏览器建立了 Google 查询标签，但读取页面连续超时；没有拿到可可靠检查的三家 SERP。通用搜索工具的域名查询也没有返回本站的可用结果，其结果不能归属为三家各自的索引状态。

### 后台复核的最小范围

| 引擎 | 最先需要的数据 | 验证目标 |
| --- | --- | --- |
| Google | sitemap 状态、页面索引原因、查询/页面效果 | 是否发现、选择了哪条 canonical、是否有实际展示 |
| 百度 | 索引量、抓取诊断、普通收录状态、流量与关键词 | 是否可读、是否被提交、哪些中文查询带来展示/访问 |

无需添加三套 SEO 元数据；先处理共同的内容完整性、分页入口与 sitemap 性能，再分别补齐可验证的提交和监测证据。

### “关键词权重”不是可以手动调节的排名参数

- Google 明确不使用 `meta name="keywords"`，该标签不影响其收录或排名。[Google 支持的 meta 标签](https://developers.google.com/search/docs/crawling-indexing/special-tags)
- Google 忽略 sitemap 的 `priority` 和 `changefreq`。当前项目也未输出这两个字段，无须添加。[Google sitemap 指南](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)
- 标题、主标题、正文和链接文字应共同描述真实主题。不要编造“标题占 40%”之类的算法比例，不设固定关键词密度，也不要把整站词表复制到每篇文章。Google 要求标题简洁、准确、独特，并避免关键词堆砌；百度公开规范也强调简洁、避免堆砌。[Google 标题指南](https://developers.google.com/search/docs/appearance/title-link)、[百度基础信息设置规范](https://ziyuan.baidu.com/college/articleinfo?id=3405)
- description 应准确概括当前页面，帮助搜索者理解结果，不应作为关键词列表。[Google 摘要指南](https://developers.google.com/search/docs/appearance/snippet)

## 补充优化：AI 时间轴明确标注来源平台（P2）

用户反馈时间轴看不出事件来自哪个平台。代码确认：`EventTimeline` 当前只显示日期、标题、摘要与“查看事件与来源”；`getEventPage` 的列表字段没有来源信息。事件详情虽然在下方“相关来源”中展示平台名称，但读者需要进入详情后才能看到。

建议范围：

- 时间轴每个事件的标题附近显示“来源：OpenAI”“来源：Anthropic”等可见文字标签，并可链接到对应来源列表页。来源图标可复用现有组件，但保留文字名称，不能只靠图标或悬浮提示辨认。
- 详情页标题区域也显示来源，保留下方具体文章与原文链接。
- 来源以现有 `ai_event_articles → signal_articles.source` 关联为依据，去重后显示；跨来源事件展示多个来源，不强行归为单一平台。缺少关联时使用明确的“来源暂缺”状态，不根据标题猜测。
- 区分“内容发布来源”和“事件涉及的平台”：例如个人博客讨论 OpenAI，来源仍应显示个人博客；不能将提到的厂商冒充发布者。本次需求先解决来源显示。
- 列表加载时批量读取当前页事件的关联来源，首批服务端 HTML 与后续分页 API 返回一致的数据，避免逐事件查询。复用已有来源配置，不需要新增来源或数据库字段。

验收：单来源、多来源、个人博客来源和缺少来源的事件均显示准确；首批 HTML 与加载更多的条目都能辨认来源；来源链接正确，现有分页、翻译与详情引用保留。此项首先改善阅读辨识与来源透明度，不承诺带来排名提升。本轮仅加入优化清单，尚未修改页面代码。
