# 业务数据库迁移到服务器 PostgreSQL

日期：2026-11-05

状态：规划，未开始实施或切换生产数据

实施记录：[业务数据库迁移](../development/business-postgres-migration.md)

## 决策与范围

- 业务数据迁到北京 ECS 上独立的 PostgreSQL 容器，复用现有 Drizzle ORM
- 应用层仅 rss-site Next.js 服务端直连数据库；浏览器、Cloudflare Worker、agent-service 不持有业务数据库凭据
- 备份、恢复、迁移属于受限运维访问，不属于应用直连方
- Supabase 暂时只保留 Auth；后台继续原有登录和 article_admin 授权，不迁移账号
- RSSHub、Redis、AI agent 保持现有职责；agent 如需业务数据，通过经过鉴权的 Next 内部接口获取
- 本期不部署完整 Supabase，不增加 PostgREST、PgBouncer 或双写系统，不调整文章保留期限
- 本文是业务数据库部署与读取路径的后续方案，替代 production-launch roadmap 中“Supabase 是唯一数据中转和 Cron 调度方”的旧目标；上线前同步相关交付规则

## 已确认的代码基础

| 范围 | 现状 | 迁移处理 |
| --- | --- | --- |
| ORM | server/api/src/db/client.ts 使用 drizzle-orm/postgres-js 和现有 schema | 复用模型和查询；核对 schema 覆盖全部业务表 |
| 页面读取 | apps/web/lib/supabase.ts 提供客户端，hot-feed、文章、首页、时间轴、Skills、日报、sitemap 等使用 Data API | 服务端 Drizzle 查询替换，保留现有分页、排序、缓存和返回契约 |
| 后台 | admin-supabase.ts 验证 Supabase 用户及 app_metadata.role，再返回 Data API 客户端 | 拆开身份验证与业务存储，授权通过后执行本地数据库查询 |
| 采集 API | server/api/src/index.ts 在 Worker 中通过 Hyperdrive 直连数据库；存在独立 Hono 采集逻辑 | 复用采集逻辑，接入 Next 的 Node runtime 路由，Worker 不再连接业务库 |
| 调度 | Supabase Cron、Vault、pg_net；另有 Worker scheduled Cookie 维护入口 | ECS systemd timer 调用受鉴权的 Next 任务入口 |
| 数据库行为 | SQL migrations 包含触发器、函数、RLS、auth.uid()/auth.jwt()、Vault 和 HTTP 通知依赖 | 按业务行为逐项迁移，不能只按 Drizzle 表结构重建 |

2026-11-05 只读检查：源库约 290 MB，文章表约 265 MB；服务器镜像清理后磁盘剩余约 19 GB。此前可用内存约 581 MB、Swap 已用约 443 MB，均为单次快照，不代表峰值容量结论。

## P0：盘点与迁移基线

- [ ] 列出全部业务表、private schema 对象、索引、外键、序列、视图、函数、触发器和实际依赖扩展
- [ ] 扫描所有 Data API/RPC、Drizzle、原生 SQL、构建期查询及独立脚本，逐项登记替换位置
- [ ] 核对独立 agent-service 仓库的日报候选读取、任务抢占、报告发布、重试及连接配置；确认所有直接读写者，不凭本仓库代码判断
- [ ] 列出线上 Supabase Cron 与 Worker 定时任务、运行时长、频率、超时、重试和秘密引用；记录新旧任务一一对应关系
- [ ] 记录源库每表行数、关键聚合、最早/最新时间、引用关系及抽样内容；不导出 Auth、Vault 明文或平台内部日志到仓库
- [ ] 采集首页、搜索、详情、后台及采集链路基线：区分缓存命中/未命中，记录延迟和数据库连接峰值

验收：所有业务读写都有明确的新入口；没有需要继续从服务器外直连新库的应用依赖

## P1：独立 PostgreSQL 与可恢复备份

- [ ] 在 rss-site Compose 增加固定版本 PostgreSQL、独立持久卷、健康检查和日志限制，不复用博客数据库实例
- [ ] 数据库不配置宿主机 ports；专用 Docker 网络仅连接 Next 和数据库，浏览器及公网无法访问 5432
- [ ] 数据库凭据仅在服务端运行时注入，不使用 NEXT_PUBLIC_，不在 Docker 构建阶段连接生产库
- [ ] 分离迁移所有者、应用权限和备份权限；Next 使用非超级用户，只授予必需的业务操作权限
- [ ] Next 复用进程级连接池，避免热重载重复创建；初始连接池上限 5，压测后再调，不引入额外连接池服务
- [ ] 明确 Next 与数据库内存预算；以 PostgreSQL 256 MB 容器限制作为试验起点，验证备份、恢复、采集和页面并发下无 OOM、无持续 Swap 增长；不通过则先扩容
- [ ] 配置每日加密异机备份、失败告警与保留周期，并在隔离库完成一次恢复；同机卷不能充当唯一备份

验收：数据库仅内网可达；备份可恢复；并发实测能覆盖现有站点和采集负载

## P2：复用 Drizzle，收拢服务端读写

- [ ] 将业务 schema/连接代码放到 Next 和采集逻辑可共同引用的服务端模块；只做所需边界调整，不顺带重构采集器
- [ ] 将现有 Data API 读取与 RPC 改为参数化 Drizzle/SQL，覆盖首页、各分区、搜索、文章、时间轴、Skills、AI 榜单、日报和 sitemap
- [ ] 保留 Supabase Auth token 验证和 app_metadata.role 检查；后台读写只能在服务端授权成功后执行，不把 JWT 解码结果直接当作身份验证
- [ ] 处理 auth.uid() 相关编辑保护触发器：本地业务库不天然知道 Supabase 用户；用明确的应用数据库角色或事务内身份上下文区分采集与管理员，保留 editorial_locked 语义
- [ ] 复用 Hono 采集流水线并挂到 Next Node runtime 任务路由，保留 CRON_SECRET 验证、超时、幂等和发布通知；不新开独立应用进程
- [ ] 将 MCP 读取、维护脚本、AI 模型入库和日报读写接到同一服务端边界；确需脚本直连时只允许服务器受限运维执行
- [ ] 将 Cookie 维护的 Vault 锁和配置依赖改为本地业务锁及服务器秘密配置，保持原有维护行为
- [ ] 迁移内容生命周期、自动时间轴、墓碑和删除发布通知；通过应用任务可靠发送失效通知并记录重试，不能丢掉现有缓存一致性
- [ ] 保留浏览器登录所需 Supabase 配置，删除业务数据对 Data API 的调用；保留公开 HTTP 返回结构，不向客户端暴露 SQL 或数据库凭据

验收：使用隔离数据库跑通真实采集、管理员编辑、日报发布和查询；未登录及非管理员写入被拒绝；不会覆盖人工锁定文章；生产流量尚未切换

## P3：迁移调度与保留清理

- [ ] 用 ECS systemd timers 替代业务 Supabase Cron 与对应 Worker scheduled，复用来源频率和错峰配置，明确时区
- [ ] timer 调用 Next 任务入口，不给调度器应用数据库连接；避免无限运行和重叠任务，保留失败与重试记录
- [ ] 日报长任务、定时补跑和失败恢复验证通过；应用重启后可以继续或安全重试
- [ ] 保留普通文章 90 天、AI 180 天、采集记录 30 天及所有保护规则；核对模型清理等代码与线上调度差异，不能将本地存在视为已上线
- [ ] 建立“对部署后的 API 和目标数据库验证全部配置来源成功，再启用调度”的新门禁，更新 setup:cron 与 AGENTS.md 中绑定云 Supabase/Vault 的旧规则
- [ ] 先验证每个来源的 run、source_status、hot_items 和字段质量，再切换任务；验证前新 timer 不得自动激活
- [x] ECS 每小时对保留的 Supabase 项目执行轻量真实数据库查询，设置超时和有限重试，不额外记录执行日志；2026-11-05 已启用并验证首次执行成功。保活不依赖 Supabase 自己的 Cron，不创建管理员密码或长期用户会话。目前查询 source_status 的一个公开 source 字段
- [ ] 业务迁移收尾时在云端保留 source_status 作为静态探测元数据，不再承担业务状态更新，保留原有只读 RLS。删除旧业务表时不得删除该探测表，除非已切换并验证其他真实数据库查询
- [ ] 将云端 Cron 日志清理列为平台任务收尾，业务调度迁走后明确保留或停用，不将它误映射为本地业务数据清理；本地 timer 日志另设轮转

验收：每项任务有唯一调度方；保留清理与发布通知联动通过；记录非秘密生产证据

## P4：全量演练与生产切换

- [ ] 从源库导出业务对象和数据，在隔离目标演练；对平台角色、RLS、Auth/Vault/pg_net 依赖明确转换，不整库盲目 restore
- [ ] 用导入后的真实数据检查 schema 兼容性、约束、触发器和序列；不能用 Drizzle push 覆盖已有 SQL 业务行为
- [ ] 验证每表行数、关键聚合、外键完整性及代表性文章、榜单、日报；比较页面内容与 SEO 输出
- [ ] 切换窗口先暂停所有写入：采集、后台编辑、日报和维护；等待在途任务结束，再生成最终一致快照并导入
- [ ] 部署 Next 新入口与连接配置，验证健康、真实读写及缓存失效后再恢复目标调度；旧 Cron/Worker 业务调度保持禁用
- [ ] 在同样请求与缓存条件下比较迁移前后延迟和并发资源占用，记录实际提速幅度
- [ ] 观察至少一个完整 24 小时周期，核验全部定时任务、备份、内存和错误率

验收：只有 Next 应用层直连业务数据库；所有业务写入新库；无双调度、无漏数据；性能无回退且资源预算通过

## P5：回滚与收尾

- [ ] 写清恢复旧应用、旧数据库配置和旧调度的步骤，保留旧源库与可用应用版本至观察期结束
- [ ] 新库尚未接受写入时可以直接回切；一旦接受新写入，必须先暂停写入并校验/回迁新增及修改数据，不能只改连接地址
- [ ] 切换失败时禁止同时恢复新旧采集；将恢复点、回迁步骤与数据核验列为回滚演练的一部分
- [ ] 稳定后撤销旧业务数据库访问配置、Hyperdrive 连接和无用调度，保留 Supabase Auth 所需配置
- [ ] 最后再处理 Supabase 旧业务表容量；独立保留的备份恢复验证成功后方可删除旧业务数据

验收：回滚过程可复现；Supabase 只承担 Auth；后续数据库变更有版本化迁移、备份和真实目标库验证
