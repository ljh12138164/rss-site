# PostgreSQL deployment

The root `compose.yaml` manages `web`, `redis`, and `postgres`. PostgreSQL uses the official `postgres:18-alpine` image, an internal network shared with `web`, and the external volume `rss-site-postgres18-data`. Port 5432 is not published.

## Configuration

- Install `deploy/postgres.env.example` as `/opt/stacks/rss-site/postgres.env`, mode 600. During migration, copy the existing protected `migration/target18.env` instead of generating a different password. Initialization variables do not change credentials in an existing database.
- Set `DATABASE_URL` in the protected `runtime.env` to the application role at `postgres:5432/rss_site`. The application must not use the `postgres` superuser.
- Provision the external volume before initial startup. The migration preparation script already creates it. Compose intentionally refuses to create a replacement volume if it is missing.
- Apply `baseline.sql` and import the data before routing production requests to this database. Do not mount the baseline into the automatic initialization directory: the rehearsal volume is already initialized.

## Adopt the rehearsal volume

PostgreSQL 18 mounts the volume at `/var/lib/postgresql`; its default data directory is `/var/lib/postgresql/18/docker`. The earlier PostgreSQL 17 rehearsal volume `rss-site-postgres-data` is preserved separately. Restore the logical source snapshot into the new PostgreSQL 18 volume `rss-site-postgres18-data` and repeat all import checks. Do not attach the PostgreSQL 17 data directory directly to PostgreSQL 18.

This is part of the migration cutover, after source writers are frozen, the final snapshot is restored and verified, and an independent backup is available. Do not run this sequence while import or validation is using the rehearsal database.

1. Save the existing application configuration and snapshot counts for rollback
2. Install `postgres.env` using the rehearsal credentials and configure the application role in `runtime.env`
3. Stop and remove only the rehearsal container `rss-site-postgres18`, retaining its data volume
4. Start `docker compose --project-directory /opt/stacks/rss-site up -d --pull never postgres`
5. Verify PostgreSQL health, database contents, grants, and application-role connectivity, then deploy the migrated web image

Never run the rehearsal container and the Compose database against the same data volume at the same time. Never use `docker volume rm rss-site-postgres18-data` for deployment or rollback. An application rollback also needs the documented writer boundary; restoring an older image does not synchronize databases.

## Operations

```sh
docker compose --project-directory /opt/stacks/rss-site ps postgres
docker compose --project-directory /opt/stacks/rss-site exec -T postgres pg_isready -U postgres -d rss_site
```

Daily backups and retention must be configured and restore-tested before production cutover. A persistent Docker volume protects data across container replacement; it does not replace a backup.

## Encrypted offsite backups

`deploy/server/postgres-backup.py` streams `pg_dump` into authenticated AES-256-GCM chunks of at most 20 MiB before uploading to the private Supabase Storage bucket `postgres-backups`. The manifest is uploaded last. Failed dumps remove their partial uploads; existing complete snapshots are retained. Keep the latest five complete snapshots and refuse uploads exceeding an 800 MiB combined archive budget. No plaintext dump is written during backup.

Install `deploy/postgres-backup.env.example` as `/etc/rss-site/postgres-backup.env` with mode 600. Fill the server-only Storage secret in this file. It must never be a `NEXT_PUBLIC_` environment variable or be included in the application image. Create the bucket as private before running a backup. A new bucket requires no public object policies.

Generate a random 32-byte key, base64-encode it, and store it in `/etc/rss-site/postgres-backup.key` with mode 600. Copy this key to an independent, protected location outside ECS before enabling the timer. The database and the Storage archive do not contain the encryption key; losing it makes every backup unreadable. The encrypted `private.maintenance_state` additionally needs the existing `MAINTENANCE_ENCRYPTION_KEY` for application recovery, so preserve that configuration independently as well.

The script requires Python `cryptography`. Install the script as `/usr/local/sbin/rss-site-postgres-backup.py`. The default container name is `rss-site-postgres-1`, generated by this repository's Compose project. During rehearsal pass `--container rss-site-postgres18` explicitly. The script refuses other PostgreSQL major versions.

Before enabling automation:

1. Run a backup and retain its non-secret snapshot identifier
2. Download and decrypt that snapshot with `--restore SNAPSHOT --output /protected/path/restore.dump`; the output path must not exist
3. Restore it into a separate, empty PostgreSQL 18 test database with `pg_restore --exit-on-error --no-owner --no-acl`; compare all business table counts and verify the application role can read the restored data
4. Remove only the disposable restore database and plaintext test archive after verification
5. Install the service and timer in `/etc/systemd/system`, then run `systemctl daemon-reload` and `systemctl enable --now rss-site-postgres-backup.timer`

The timer runs at 03:00 Asia/Shanghai (19:00 UTC the preceding day). A successful upload is not a restore test. Repeat the download and isolated restore after schema changes. Monitor the service exit status; a failed backup or a full storage budget must not be treated as success.

`python deploy/server/test-postgres-backup.py` checks multipart encryption/decryption, ciphertext corruption, authentication failure, output overwrite protection, incomplete dump cleanup, five-snapshot retention, and storage-budget enforcement. These tests do not replace the real Storage upload and PostgreSQL restore gate.
